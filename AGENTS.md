# Project Overview
- FTC robot controller codebase focused on Road Runner–driven mecanum control with AprilTag localization and sample detection.
- Main control entry point is `TeamCode/src/main/java/org/firstinspires/ftc/teamcode/DecodeRobotControl.java`, which wires hardware (pinpoint odometry, webcam, color sensor, shooter wheel, lift servo, mecanum drive) and coordinates teleop/autonomous behavior.
- `DecodeRobotControl` is constructed and driven only from `TeamCode/src/main/java/org/firstinspires/ftc/teamcode/DecodeOpMode.java`, which initializes the robot, starts camera streaming to the dashboard, and repeatedly calls `evaluate()` while the op mode is active.
- Current loop handles manual driving, command-sequence execution, AprilTag-based pose updates, and dashboard telemetry logging/streaming; many TODOs remain and the system is a WIP baseline for future functionality.
- Robotics/game-specific configs live in `Constants` and related utilities (e.g., `AllianceColor`, `OnActivatedEvaluator`); extend these as new mechanisms and autonomous plans are added.
- Shooter geometry/control: shooter wheel lives inside a rigid thrower arc with ~135° of contact, grabbing the ball at the top and accelerating it along the spine to exit at ~45° with some top spin from friction. Motor is set to float; off mode uses 0 power, on mode targets an exit-velocity range via `gamepad2.right_trigger` (see shooter constants and mapping in `DecodeRobotControl`), translating desired ball speed to wheel surface/tick velocity.
- Shooting targets/auto-speeding: field origin at center; rim height 39" with a 5" ball requiring clearance (target plane = rim height + radius). Basket anchors: red (-72, 72), blue (-72, -72) in inches. Shooter is offset ~5" to the right of robot center (negative lateral) and uses the robot heading. When the shooter is enabled, `DecodeRobotControl` continuously computes a ballistic solution toward the alliance basket using a fixed 50° exit angle (contact arc shortened to ~130°), measured ball exit height of ~15.75" (bottom of ball at 13"), and a top-spin drop model derived from rolling through the contact arc vs exit speed. Wheel velocity uses a tunable transfer ratio (base 0.8) trimmed additively by ±0.1 via triggers (right trigger extends/longens, left trigger shortens) within safety bounds; falls back to trigger-scaling if no pose/solution. Telemetry exports the shot solution (speed, distance, effective gravity, spin, transfer ratio, tangential speed) and draws the predicted rim-plane intersection (using shooter pose/heading) on the field overlay; if the solver predicts the trajectory cannot clear the rim, the overlay marks the basket with an X instead of an intercept point.
- Ball path: rear intake with rubber-band rollers pulls balls upward along a friction wall into a three-slot spindexer; a specific slot (1–3) must be presented to the collector to receive the ball cleanly.
- Spindexer geometry/control: three pockets 120° apart, driven by a multi-turn servo calibrated via `SPIN_SERVO_RANGE_DEGREES` (measured ~1630°, not the advertised 1800°). Slot-to-slot spacing is derived from that measured range (120° spacing). Slot 0 collect alignment is set by `SPIN_BASE_POSITION_COLLECT` and needs field calibration; the system initializes slot 0 collect to the midpoint-adjacent position so early moves can go either direction.
- Shooting alignment: the kicker wants the same pocket rotated about 2/5 of a turn (~144°) from the collect position. Control computes a canonical target for the active slot/mode and uses shortest-path selection across the multi-turn range (wrap-aware) to minimize travel. The kicker is a 270° servo (`kicker`) with tunable positions (default unkicked 0.2, kicked ~0.57 for ~100° travel). Teleop: `gamepad2.left_bumper` toggles the kick; leaving SHOOT mode auto-returns to unkicked. Telemetry exports target and servo positions for tuning.
- Spindexer teleop controls (gamepad2): `x` next slot, `b` previous slot (wraps 1–3), `dpad_up` SHOOT mode, `dpad_down` COLLECT mode. Telemetry exports `SpindexerSlot` (1-based), `SpindexerMode`, canonical/target/command/servo positions, and delta for tuning.
- Game piece mix/patterning: the three-slot spindexer implicitly tracks up to three balls. Game pieces are green and purple, with roughly 2:1 purple:green supply. Each match uses a fixed pattern indicating whether the green ball appears first, middle, or last in any 3-ball sequence; the pattern is encoded by an AprilTag obelisk on the field perimeter with IDs 21 (green first), 22 (green middle), or 33 (green last). Baskets drain into a classifier that queues up to nine balls in order before a robot releases them downstream, so preserving the correct slot order matters for scoring interpretation.
- Localization: AprilTag-based pose updates run in `DecodeRobotControl.evaluatePositioningSystems()`, pulling fresh detections from the AprilTag processor and filtering by range/bearing/yaw thresholds from `Constants`. Tag poses/rotations come from `AprilTagGameDatabase.getDecodeTagLibrary()`; tag headings are mapped in `getTagFieldHeading(...)`.
- Camera mounting: supports forward/lateral offsets and an optional yaw offset between the camera and robot forward; pitch/height are not yet used in math. The robot pose is derived by translating the camera pose back through those offsets.
- Pose computation: converts tag detection (ftcPose range/bearing/yaw) into camera pose in field frame, then subtracts the camera offset to get robot pose. Uses an 8-sample queue to average poses; applies variance gating before pushing to the Road Runner pose estimate (skips updates in autonomous).
